# P3 v42.0-48 — аппаратный запуск TIMER3 по GPIOTE/PPI

**Статус: эксперимент. Не подтверждена компиляция, ток, качество UART и корректность на HW-954. Только тестовая штора №3.**

## Что меняется

- P0.17 продолжает использовать GPIO-прерывание Zephyr для пробуждения.
- Если драйвер Zephyr выделил GPIOTE IN на падающий фронт и доступен PPI-канал nrfx, аппаратное событие запускает TIMER3 непосредственно по фронту RX.
- GPIO callback больше не перезапускает TIMER3 в этом случае.
- Во время приёма байта PPI отключается, чтобы дополнительные переходы RX не изменяли тайминг.
- Если PPI/GPIOTE недоступен или TIMER3 не начал отсчёт, остаётся прежний путь GPIO IRQ → TIMER3.
- После первого байта 0x55 продолжается существующий UARTE0 + EasyDMA.
- **Никаких изменений** Zigbee poll, моторных команд, калибровки, DP1/DP3, STOP guard 1500 ms, watchdog 120 s.

## Диагностика Z2M — Basic cluster

| Поле | Атрибут | Интерпретация |
|---|---|---|
| ppi_enabled | 0xF187 | 1 = PPI-канал выделен; 0 = fallback, эксперимент фактически не запущен |
| ppi_starts | 0xF188 | Количество входов в стартовый декодер с PPI |
| ppi_fallbacks | 0xF189 | Количество запусков через исходный IRQ-путь |
| ppi_late_irqs | 0xF18A | GPIO callback пришёл после порога 156 мкс; возможно позднее декодирование |

**Ограничение:** счетчик ppi_starts показывает срабатывание PPI-схемы по счётчику TIMER3, но не доказывает успешное декодирование стартового байта. Нулевые UART-ошибки в одном тесте также не доказывают отсутствие потерь.

## Порядок проверки

1. Выполнить CI-компиляцию, тесты исходников и проверку UF2. Пока CI не подтверждена — **не прошивать**.
2. Сохранить v42.0-47 UF2 как резервную.
3. Прошить только тестовую штору №3; не изменять плату и проводку.
4. Прочитать swBuildId = 42.0-48 и ppi_enabled. При ppi_enabled=0 PPI не работает — анализ потребления в этом варианте не показателен.
5. Проверить команды OPEN / CLOSE / STOP, вручную наблюдая правильное положение.
6. После 20 циклов приёма/движения зафиксировать ppi_starts, ppi_fallbacks, ppi_late_irqs, rx_framing_errors, rx_ring_overflows, tuya_frames_ok, hw_direct_max_timeouts и hw_direct_active.
7. Проверить переходы из движения в покой и приём сообщений MCU в покое, в том числе через 1–2 часа. Сравнить все счётчики с предыдущей v42.0-47.
8. Отдельно измерить реальный ток nRF52840 в простое. Цель — сохранить около 0.03–0.05 мА при сравнимых условиях, не считать это значение заранее достигнутым.

## Риски

- Возможна задержка запуска высокочастотного тактирования после простоя; PPI не гарантирует исправный приём самого первого байта.
- Реальное распределение GPIOTE/PPI-ресурсов зависит от Zephyr, ZBOSS и конфигурации сборки. Если канал занят — должен применяться fallback.
- Для физически защищённого мотора P3 сохранённые пределы ограничивают ход, но если приём потеряет DP1=STOP, прошивка всё ещё может держать UARTE0 до 120 секунд.
- Новая логика выключения аппаратного UART по достигнутому положению **не входит в v42.0-48**, чтобы отделить две разные причины ошибок и экономии.

## Критерий продолжения

Если v42.0-48 проходит аппаратные испытания, следующим отдельным экспериментом исследовать завершение аппаратного RX по надёжно подтверждённому целевому DP3 плюс пауза без RX-трафика, сохранив независимый watchdog и не отправляя дополнительный STOP мотору.
